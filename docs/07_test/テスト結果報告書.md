**不具合は検出されなかった。★T2(R-14)・★T3(大容量)の修正を再確認し、いずれも修正どおりに動作した。テスト完了の3条件を満たしており、「完了」と判定する(★T1=TC-103は納品フェーズで依頼者ご本人が確認し合格。v2.3)。**

- v2.2の再確認結果(修正コミット6c3b2fb・3de4abf・c16a1c6、詳細設計書v2.5)
  - ★T3: 見込みサイズが1GiBを超えるエクスポートは、保存ダイアログの前に中止され、専用文言「領収書・PDFの容量が復元できる上限(1GB)を超えるため、エクスポートを中止しました。復元できないファイルになってしまうため、書き出していません」が表示される。`confirmLarge`付きでも同じで、実ファイル約1.05GiB(108件)でもZIPは作られない。1GiBちょうど・80%超は従来どおり警告+続行で、80%ちょうど(858,993,459バイト)は警告なし。復元側は1GiB超のファイルで専用文言「ファイルの容量が復元できる上限(1GB)を超えているため、読み込めませんでした」が出て、データは変わらない(TC-94・TC-99・TC-104)
  - R-22: 約760MBのエクスポートで、ファイル書き出しの進捗(80/80)の後、約12秒間「ファイルを整理しています…」が画面(Renderer)に表示されることを確認した。ZIP生成中はMainプロセスが同期処理でブロックされ、スクリーンショットが取得できないため、Renderer内のDOM観測(表示されている・文言・開始時刻)をエビデンスとした(TC-104_01.txt)
  - ★T2(R-14): すでに入金済みの請求書へ再度「入金済み」を指定すると「この請求書はすでに入金済みです」が表示され、請求書・入金記録は変わらない(TC-98)
  - 回帰: 既存の結合シナリオ47件+配布物3件(再作成した`.app`)、i2系シナリオ(23件+TC-104)、単体745件・開発者E2E 3件・★R5の10回繰り返しがすべて成功し、回帰はない
  - 残課題(未対応): メインプロセスのメモリ使用量(扱うデータの約3倍。760MBで約2.7GB)は今回の修正の対象外で変わらない(★T3⑤)

- 重点観点の結果
  - 改変検知(電子帳簿保存法対応): 領収書ファイルの改ざん・欠落・保存先の不正、記録のDB直接改ざん、記録ハッシュの書き換え、復元ZIPの改ざん(領収書・記録・履歴ハッシュ)を、いずれも検知・通知できた。通常操作(登録・更新・領収書の追加と外す・取消・復元)での誤検知はない。改ざんされた領収書を「開く」前の警告(中止ならOSに渡さない)も確認した(TC-86・TC-87・TC-93)

##### BUG-01(i1)(TC-51、重大度: 中)

**v1.2の確認結果: 解消**(コミット362e626。画面が下書きIDを保持して再試行時に同じ下書きを確定する。見積書・請求書とも再現手順どおりに実機で再確認し、下書きは重複せず1件、書類番号は欠番の次の2026-002)。

- **現象**: 新規作成画面で「PDFとして保存」がPDF生成・書き込みの失敗で「PDFの保存に失敗しました」となった後、同じ画面でもう一度「PDFとして保存」を押すと、失敗時に下書きへ戻したレコードとは別のレコードが作られる。失敗時の下書き(未採番)が残るため、見積書一覧に同一内容の下書きが重複する。書類番号は欠番の次(2026-002)で正しく採番される
- **再現手順**:
  1. 自社情報・取引先を登録する。データ保存先の`documents`フォルダを書き込み不可にする(例: `chmod 500 <データ保存先>/documents`。テスト用の一時保存先のみ)
  2. 見積書の新規作成画面で取引先・品名・単価を入力し「PDFとして保存」を押す(「PDFの保存に失敗しました」が表示され、作成画面に留まる)
  3. `documents`フォルダの権限を戻し、同じ画面でもう一度「PDFとして保存」を押す(「PDFとして保存しました」で2026-002が採番される)
  4. 一覧画面を開く(2026-002の確定済みに加え、未採番の下書きが1件残っている)
- **原因(コード参照のみ)**: `QuoteFormPage.tsx`(請求書は`InvoiceFormPage.tsx`)の`handleFinalize()`が、失敗時に`quoteId`(新規作成画面では未指定)を更新しない。`QuoteService.finalizeQuote()`は`id`未指定の場合に新規INSERTするため、1回目の失敗で作られた下書きのIDを画面が保持せず、2回目で別のレコードが作られる
- **影響**: PDF保存に失敗した利用者が再試行すると、見積書・請求書の下書きが重複する。データ自体は壊れないが、一覧に不要な下書きが残る
- **修正確認の区分**: 三段階を推奨(F-12・F-14の2機能にまたがり、確定処理の失敗時の画面状態の設計に関わる)

#### 4.1 v0.0初回テストで検出した不具合の詳細・再現手順(経緯の記録。両件ともv0.1で解消済み)

##### BUG-01(TC-02、重大度: 高)

- **現象**: データ保存先ディレクトリに有効なSQLiteファイルではない`data.sqlite`が存在する状態でアプリを起動すると、詳細設計書4.1章手順5が定める「起動エラー画面」が表示されず、**ウィンドウが一切表示されないまま無反応になる**(10秒待ってもElectronの"window"イベントが発火しない)。
- **再現手順**:
  1. テスト専用のデータディレクトリを用意し、`data.sqlite`として不正な内容(有効なSQLiteファイルではない文字列)のファイルを事前に配置する
  2. `JIMUHUB_DATA_DIR`に上記ディレクトリを指定してアプリ(Electron)を起動する
- **原因(コード参照のみ、修正はdeveloper対応)**: `app/src/main/index.ts`の`app.whenReady().then(() => { const database = new Database(dbFilePath) ... })`において、`new Database(dbFilePath)`の呼び出しがtry/catchの**外側**にある。`app/src/main/db/db.ts`の`Database`コンストラクタは`openConnection()`内で`connection.pragma('journal_mode = WAL')`を同期的に呼び出しており、DBファイルの中身が不正なSQLiteファイルの場合はこの時点で例外が発生する。try/catchは`database.initialize()`の呼び出しのみを囲んでいるため、コンストラクタ時点の例外を捕捉できず、`app.whenReady().then()`のコールバック全体が未処理の例外で中断し、`createMainWindow()`が一度も呼ばれない。
- **影響**: 詳細設計書が明示的に定めた異常系シナリオ(データベースファイル破損)において、エラー画面より重大な「無反応」状態になる。利用者には強制終了以外の復旧手段がない。
- **推奨対応区分**: エラーハンドリング設計(詳細設計書8章)に関わる修正のため、**三段階(developer修正後、reviewerへの再レビューを挟んでからtesterが再確認)**を推奨する。
- **エビデンス**: `docs/07_test/evidence/TC-02_startup-error/`(`02_failure_trace.zip`をPlaywrightの`show-trace`で参照可能、`03_failure_log.txt`に直接起動した際の標準エラー出力を記載)

##### BUG-02(TC-29・TC-31、重大度: 中)

- **現象**: 取引先詳細画面で「利用停止にする」→「はい」を実行すると、完了メッセージ「取引先を利用停止にしました」は表示され、バックエンドのデータ自体も正しく`status: inactive`に更新される(`window.jimuhubApi.getClient()`で直接確認済み)が、**同一の詳細画面インスタンス内ではバッジ・「編集」ボタンの表示が「利用中」のまま**残る。一覧へ戻ってから同じ取引先を開き直す(画面を再マウントする)と、正しく「利用停止」の表示になる(`docs/07_test/evidence/TC-31_client-lifecycle/10_detail_fresh_mount_after_deactivate.png`で確認済み)。
- **再現手順**:
  1. 取引先を1件新規登録する
  2. 一覧からその取引先の詳細画面を開く
  3. 「利用停止にする」→確認ダイアログで「はい」を押す
  4. 同じ詳細画面内のバッジ・「編集」ボタンの表示を確認する(「利用中」のまま、「編集」も活性のまま)
- **原因(コード参照のみ、修正はdeveloper対応)**: `app/src/renderer/src/pages/ClientDetailPage.tsx`の`useEffect`の依存配列が`[clientId]`のみであり、利用停止操作後も`clientId`自体は変わらないため再フェッチのトリガーにならない。`app/src/renderer/src/App.tsx`の`onDeactivated`は同じ`id`で`route`を更新するのみで、`ClientDetailPage`は`key={route.id}`のため再マウントされない。
- **影響**: 詳細設計書4.8章手順4「一覧・詳細画面の表示を最新化し、状態バッジを反映する」に反する。データ自体は正しく、画面遷移をやり直せば正しい表示に戻るため実害は限定的だが、利用者が同一画面内で一時的に誤った状態(利用停止にしたのに「編集」ボタンが押せるように見える)を見てしまう。
- **推奨対応区分**: `ClientDetailPage.tsx`単一コンポーネントに閉じた軽微な修正のため、**二段階(developer修正後、testerが直接実機再確認)**で問題ない。
- **エビデンス**: `docs/07_test/evidence/TC-31_client-lifecycle/10b_bug_TC-31-a_stale_badge.png`・`10c_bug_TC-31-a_trace.zip`・`10d_bug_TC-31-a_note.txt`(再現手順の詳細)。なお同シナリオの他のステップ(登録・一覧反映・詳細表示・編集・件数連動・一覧からの除外・「利用停止も表示」での再確認・再マウント後の正しい表示)はすべて合格しており、不具合はこの箇所に限定される。
