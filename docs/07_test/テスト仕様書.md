### 2.2 テスト環境

- OS: macOS(Darwin 25.6.0、arm64)、Node.js v25.2.1、Electron 44.4.5(`app/package.json`記載)
- 実行方式: `npm run build`でビルドしたコードを、Playwright(`_electron`)経由でElectronプロセスとして実機起動する。配布物の確認は`electron-builder --mac --dir --arm64`で一時ディレクトリへ作成した`.app`を起動する
- **データの隔離(必須ルール)**: 実機でアプリを起動する場合は、必ずデータ保存先を一時ディレクトリへ指定する。開発ビルドは`JIMUHUB_DATA_DIR`、配布版は`--user-data-dir=<一時ディレクトリ>`を用いる(配布版は`JIMUHUB_DATA_DIR`を無視するため)。**実データ(`~/Library/Application Support/事務HUB`)には一切触れない**
- OS標準ダイアログ(保存・選択)は、E2E専用の環境変数(`JIMUHUB_E2E_EXPORT_PATH`・`JIMUHUB_E2E_IMPORT_PATH`)で省略する(配布版では無効)。PDFを実際に開く操作(`shell.openPath`)は自動テストでは押下しない(納品フェーズで確認)
- PDFの内容確認: macOS標準のPDFKit(`swiftc`でビルドした補助ツール`e2e/scenarios/tools/pdf-text.swift`)でテキストを抽出し、`sips`で1ページ目を画像化する。DBの確認はmacOS標準の`sqlite3`(読み取り専用)で行う

## 4. テスト方針・実施方法

### 4.1 実施方法の内訳

事前確認の回答(project-leader経由でユーザー承認済み)に基づき、以下の方針で実施する。

1. **実機自動確認(主軸)**: developer整備済みのPlaywright(`_electron`、Electron実機起動)基盤を、テスター自身が`app/e2e/scenarios/`配下に追加した補助スクリプトから再利用し、機能横断シナリオ(観点⑤)を含めて自動実行する。証拠としてスクリーンショット・実行ログを取得する。既存のfixture(`app/e2e/fixtures/electron-app.ts`)をそのまま再利用し、`app/src/`(実装コード)は一切変更しない。
2. **実機手動確認(補助)**: OS標準ダイアログ等、自動化が困難な項目に限定する(4.2節参照)。
3. **静的確認**: コードカバレッジの数値確認、デザイントークン(CSS変数)の静的比較など。

### 4.2 自動化困難な項目の扱い

以下は自動化が困難なため、テスターの実機確認範囲から除外する。**ユーザーの判断により、イテレーション0と同様に納品フェーズ(deployer・操作マニュアル検証時)の確認へ持ち越し、テスト完了条件の判定には含めない**(テスト結果報告書5.3章に手順・期待結果を記載)。自動で代替できる部分(ファイルの出力有無、PDFの生成・内容、案内文言の表示)はテスターが実施する。

- OS標準のファイル保存・選択ダイアログの実際の見た目(TC-35・TC-36)
- Gatekeeper警告(未署名配布)の表示・許可手順(TC-37)
- `.dmg`のマウント・Applicationsフォルダへのインストール(TC-38)
- 「PDFを開く」「Finderで表示」のOS連携の実機動作(TC-75)
- PDFの見た目(複数ページのフッター・フォント等)の目視(TC-76)
- Dock・Finderでのアイコンの実表示(TC-77)
- (イテレーション2で追加)領収書の「開く」「Finderで表示」のOS連携、CSVのExcel等での表示、領収書追加・CSV保存のOS標準ダイアログ(TC-103)
- スクリーンリーダー等の読み上げ(確認依頼の対象外。必要になった時点で別途確認)

### 4.3 合否判定基準

- 期待結果(詳細設計書の記載どおりの動作)と実際の結果が一致すれば「合格」、一致しなければ「不合格」とし、再現手順・重大度を記録する
- 自動化困難で実施していない項目は「未実施(納品フェーズへ持ち越し)」とし、要確認事項として扱う(不合格には含めない。完了条件の判定対象外)
- (イテレーション2)OSのアプリ起動(`shell.openPath`・`showItemInFolder`)・確認ダイアログ(`dialog.showMessageBox`)は、テストではメインプロセス側を差し替えて呼び出しと文言を確認する(実際には起動・表示しない)。1GiB閾値は設定で変更できないため、DB上の領収書サイズ合計を書き換えて警告条件を再現し、1GiB超は実ファイル(約1.05GiB)で実測する
- (イテレーション2)デザインガイド適合(computed style)の再実測は、ユーザー確認済みの観点(機能・異常系・データ整合性・回帰・結合)に含まれないため今回は対象外とし、新画面の見た目はスクリーンショット(エビデンス)の目視に留める
- developerの単体テスト・E2Eテスト(README.md 5章)は、コードカバレッジの計測のために単体テストを再実行し、E2Eテスト(2件)も回帰確認として再実行する

- 基準値: 行(Lines)80%・分岐(Branches)70%(イテレーション0と同じ。ユーザー確認済み)
- 計測コマンド: `npm run test:coverage`(`vitest run --coverage`。v8プロバイダ。計測対象は`src/**/*.{ts,tsx}`のテストファイルを除く全ファイル)。README.md 5.1章に計測値の記載がなかったため、テスターがテスト用設定(`vitest.config.ts`の`coverage`、`@vitest/coverage-v8` 5.0.2を`devDependencies`へ追加、`package.json`の`test:coverage`スクリプト)を追加して計測した(実装コードは変更していない)
- 判定: 実測値を基準値と照合し、未達の場合は不合格として実装へ差し戻す(テスト追加を依頼)

## 7. エビデンス方針

- 保存先(イテレーション2): `docs/07_test/evidence/iteration-2/`(実行ログは`iteration-2/_run_logs/`)。運用ルールはイテレーション1と同じ。テキストのエビデンス中のローカル絶対パスはプレースホルダーへ置換済み。スクリーンショットに写る保存先は、OSの一時ディレクトリ(ユーザー名を含まない)のみである
- 保存先: イテレーション1の公式エビデンスは`docs/07_test/evidence/iteration-1/`に保存する。イテレーション0のエビデンス(`docs/07_test/evidence/`直下の`TC-*`フォルダ・`_run_logs*`)は移動・上書きせず、そのまま保持する(今後のイテレーションも`iteration-N/`を追加する)
- ファイル名: `<TC-ID>_<連番>.<拡張子>`(例: `TC-48_03.png`)。1つのTC-IDに複数の証跡がある場合は連番を増やす。各ファイルの説明は同フォルダの`_index_<日時>.txt`に記載する(実行ログは`iteration-1/_run_logs/`)
- 形式: 画面操作の確認はスクリーンショット(PNG)、PDFの確認は抽出テキスト(TXT)と1ページ目の画像(PNG)、処理・DBの確認は実行ログ・照合結果(TXT)
- **上書き防止の運用ルール**:
  1. シナリオ実行時の出力先は、環境変数`JIMUHUB_EVIDENCE_DIR`で指定する。未指定の場合はOSの一時ディレクトリ(`<tmpdir>/jimuhub-evidence-run`)へ出力する
  2. `docs/07_test/evidence/`配下を出力先に指定するとシナリオがエラーで停止する(`app/e2e/scenarios/evidence-dir.ts`)。公式保存先へ直接書き出さない
  3. 合格を確認した成果物のみ、`app/e2e/scenarios/tools/promote-evidence.sh <実行出力ディレクトリ> <イテレーション番号>`で`iteration-<N>/`へコピーする(既存ファイルは上書きしない。traceのzipは絶対パスを含むため対象外)
  4. フォローアップテストで再実行した場合は、環境変数`JIMUHUB_EVIDENCE_SEQ_BASE=<docs/07_test/evidence/iteration-1の絶対パス>`を指定して実行する。既存ファイルの連番の次から採番され、過去のエビデンスは削除も上書きもしない(v1.2で追加)
- 実施日時・実行環境: テスト結果報告書.md 1章、および`iteration-1/_run_logs/`の実行ログに記録する
- マスキング: スクリーンショットの表示内容はすべて架空のデータ(例: 「試験用デザイン事務所」「通しシナリオ株式会社」)を使用する。ログ・テキスト中のローカル絶対パスは`<project-root>`・`<tmp>`・`<scratch>`等のプレースホルダーへ置換してから保存する
