## 2. テスト概要

### 2.1 対象範囲

機能仕様書・詳細設計書のF-01〜F-08(アプリ起動・基本画面、データエクスポート、データ復元、取引先の登録・一覧表示・参照・更新・削除(利用停止))を対象とする。フェーズ2以降の案件管理・見積請求・入出金経費・タスク管理は対象外(未実装)。

### 2.2 テスト環境

- OS: macOS(Darwin 25.6.0)
- 実行方式: Electronアプリの実機起動(`npm run build`でビルドしたコードを、Playwright(`_electron`)経由でElectronプロセスとして起動)
- データ保存先: すべてテスト専用の一時ディレクトリ(`JIMUHUB_DATA_DIR`環境変数で指定)に隔離し、本番のデータベースファイル(`~/Library/Application Support/事務HUB`)には一切影響しない
- Node.js: README.md 7章★D2のとおり、動作確認バージョンと依存パッケージの推奨バージョンに軽微な差異があるが、テスト・ビルドの動作に問題がないことを確認済み

### 2.3 前提条件

- 実装(developer)・レビュー(reviewer)がいずれも完了しており、レビュー結果報告書.md v0.1で「テストへ進めることを推奨する(合格)」の判定を受けていること
- developerの単体・画面操作テスト(Vitest、139件)およびE2Eテスト(Playwright、2件)がすべて成功していること(README.md 5章)

## 3. テスト観点

以下5分類を用いる。機能ID(F-01〜F-08)ごとに、該当する観点のみ適用する(トレーサビリティ表(6章)に適用方針を明示する)。

| 観点 | 定義 |
|---|---|
| ① 機能テスト | 詳細設計書の画面詳細設計(3章)・処理フロー設計(4章)・API設計(7章)どおりに動作するか |
| ② 異常系・入力値検証 | エラーハンドリング設計(8章)どおりに異常系が処理されるか |
| ③ データ整合性 | DB詳細設計(6章)どおりにデータが登録・更新・参照されるか。特にF-03の全置換・3世代退避・ロールバックを重点確認する |
| ④ 回帰確認 | 既存の合格項目(developerのE2E・レビュー確認済み事項)が崩れていないか |
| ⑤ 機能横断・結合確認 | 複数機能にまたがる画面遷移・データの受け渡し・レイアウトの全体整合性(単体テスト・機能単位レビューでは見えない不整合がないか) |

上記に加え、依頼者ヒアリングで承認された範囲(project-leader事前確認回答)に基づき、次の観点も併せて確認する。

- デザインガイド適合: デザインガイド.md 5章「部品カテゴリーのルール」(色・角丸・危険色の使用範囲)との一致を、実際にレンダリングされたcomputed styleで確認する
- 性能: 取引先50件程度投入時の一覧表示・検索の応答性(体感の遅延有無)

## 4. テスト方針・実施方法

### 4.1 実施方法の内訳

事前確認の回答(project-leader経由でユーザー承認済み)に基づき、以下の方針で実施する。

1. **実機自動確認(主軸)**: developer整備済みのPlaywright(`_electron`、Electron実機起動)基盤を、テスター自身が`app/e2e/scenarios/`配下に追加した補助スクリプトから再利用し、機能横断シナリオ(観点⑤)を含めて自動実行する。証拠としてスクリーンショット・実行ログを取得する。既存のfixture(`app/e2e/fixtures/electron-app.ts`)をそのまま再利用し、`app/src/`(実装コード)は一切変更しない。
2. **実機手動確認(補助)**: OS標準ダイアログ等、自動化が困難な項目に限定する(4.2節参照)。
3. **静的確認**: コードカバレッジの数値確認、デザイントークン(CSS変数)の静的比較など。

### 4.2 自動化困難な項目の扱い

以下は自動化が困難なため、テスターの実機確認範囲から除外し、「要確認事項」としてユーザー自身に確認いただく(テスト結果報告書5章に手順を記載する)。

- OS標準のファイル保存・選択ダイアログの実際の見た目(初期フォルダ・初期ファイル名・拡張子フィルタの効き)
- Gatekeeper警告(未署名配布)の表示文言・許可手順
- スクリーンリーダー等のアクセシビリティ読み上げ
- `.dmg`のマウント・Applicationsフォルダへのインストール操作(developerが`.app`の直接起動までは確認済み。`.dmg`インストール自体の実機確認は、事前確認の回答により納品フェーズ(deployer)の操作マニュアル検証時に行う)

### 4.3 合否判定基準

- 期待結果(詳細設計書の記載どおりの動作)と実際の結果が一致すれば「合格」、一致しなければ「不合格」とし、再現手順・重大度を記録する
- 自動化困難で実施していない項目は「未実施」とし、要確認事項として扱う(不合格には含めない)
- developerの単体テスト・E2Eテスト(README.md 5章)の結果は参照するに留め、原則再実行しない(コードカバレッジの検証に必要な場合のみ計測コマンドを再実行する)

## 5. カバレッジ基準

### 5.1 仕様カバレッジ

詳細設計書の全機能ID(F-01〜F-08)と、5分類の観点(3章)との対応表(6章トレーサビリティ表)を作成し、テストケースが割り当てられていない空欄がないことを確認する。観点を適用しない場合は「対象外」とし理由を明記する。

### 5.2 コードカバレッジ

- 基準値: 行(Lines)80%・分岐(Branches)70%(推奨値どおり採用)
- 判定方法: README.md 5.1章には実行結果(139件成功)の記載はあるが、カバレッジの実測値(%)は記載がないため、`npx vitest run --coverage`(`@vitest/coverage-v8`を`--no-save`で一時導入)を実行して計測し、基準値と照合する
- 対象: `app/src/`配下の全ファイル(Main・Preload・Renderer・Shared)

## 7. エビデンス方針

- 保存先: `docs/07_test/evidence/`配下に、テストケースID(またはシナリオ名)単位でサブフォルダを作成する
- ファイル名: `<TC-ID>_<連番>.<拡張子>`を基本とし、シナリオが複数のTC-IDにまたがる場合はシナリオ名フォルダ配下に連番で保存する(テストケース.md・テスト結果報告書.mdから該当フォルダを参照する)
- 形式: 画面操作の確認はスクリーンショット(PNG)、コマンド実行・API呼び出しの確認は実行ログ(TXT)、失敗時の詳細な再現確認にはPlaywrightのtrace(ZIP、`npx playwright show-trace`で参照可能)を用いる
- 実施日時・実行環境: `docs/07_test/evidence/_run_logs/`配下の実行ログ、および本書2.2節・テスト結果報告書1章に記録する
- マスキング: スクリーンショットの表示内容はすべて架空のデータ(例: 「結合シナリオ商事株式会社」等、実在しない社名)を使用し、実在の個人情報は使用しない。ログ・テキスト中のローカル絶対パスは`<project-root>`等のプレースホルダーに置換する
