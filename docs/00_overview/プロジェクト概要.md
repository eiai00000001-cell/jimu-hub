# プロジェクト概要

## 1. 文書情報

- 作成日: 2026-09-28
- 版数: v3.2
- 対象イテレーション: イテレーション3(案件管理+バックアップ・復元のメモリ使用量改善)
- 参照元: イテレーション総括.md v3.0(docs/10_summary。6章・7章)、スコープ確認結果(2026-10-06)。アイデアメモ.mdは今回追記なし

## 2. プロジェクトの目的・背景

「事務HUB」は、個人事業主である依頼者ご本人が日々行う事務作業を一つのツールに集約し、効率的に管理できるようにすることを目的として開発する。対象とする業務は、見積書・請求書の作成、入出金・経費の記録、取引先・案件の管理、タスク・期限の管理である。現時点でこれらの業務を管理している既存ツールは無く、今回新規に構築するものであり、既存システムからのデータ移行は発生しない。

## 3. 対象ユーザー・利用シーン

- 利用者: 依頼者ご本人のみ(唯一の利用者であり、複数ユーザーでの利用は想定しない)
- 利用端末: PCを中心とする
- 想定利用シーン: 見積書・請求書の作成、日々の入出金・経費の記録、取引先や案件情報の参照・更新、タスクや期限の管理など、個人事業の運営に伴う事務作業全般

## 4. 技術スタック・制約(初回確定分)

- 提供形態: インターネットには公開せず、ローカル環境のみで動作するデスクトップアプリケーションとする。
- 認証: 認証機能は設けない方針とする。PC自体のログイン・画面ロックによって保護することとする。ヒアリング当初は「ログイン必須」案も挙がったが、ローカル専用のデスクトップアプリであるという特性を踏まえ、「認証なし」に決定した。
- 具体的な使用言語・フレームワーク・データベース等の技術選定は、イテレーション0の設計フェーズ(基本設計書.md・詳細設計書.md)にて確定済みであり、イテレーション1以降はこれを前提として踏襲する。イテレーション1のPDF出力機能の技術要素も確定済みであり、同様に踏襲する。イテレーション2の技術要素(領収書ファイルの保存方式、CSV出力の形式・文字コード等)も確定済みであり、同様に踏襲する。イテレーション3で新たに必要となる技術要素(バックアップ・復元のストリーミング方式、案件と各データの紐づけ方式等)の選定は、次フェーズ(architecture)にて確定する。
- デザイン担当: designer(業務用のデスクトップツールであり、デザイン重視の制作案件ではないため。イテレーション1・2の実績を継続する)。

## 5. セキュリティ・法令面の方針

- インボイス制度(適格請求書等保存方式)への対応: イテレーション総括.md(v1.0)で申し送られていた依頼者のインボイス登録状況(★7)について、イテレーション1のスコープ確認で「登録・未登録の両方に対応する」方針が確定した。設定画面にインボイス登録番号を入力した場合にのみ、見積書・請求書に適格請求書等保存方式の記載事項(登録番号等)を表示する。登録番号が未入力の場合は、区分記載請求書等の形式で出力する。
- 電子帳簿保存法への対応: ★8について、最小限の対応水準として「発行した見積書・請求書等の文書を改変せずに保存し、日付・金額・取引先の各条件で検索できるようにする」方針が確定した(イテレーション1で実装済み)。イテレーション2では、この水準(改変検知、日付・金額・取引先での検索)を入出金・経費の記録にも適用し、添付する領収書ファイル(PDF・画像)も同水準で扱った。イテレーション3で見積書・請求書・入出金・経費を案件に紐づける際も、この水準を損なわない(紐づけによって、発行済み書類の改変検知や検索条件に影響を与えない)ことを前提とする。詳細は設計フェーズで確定する。
- 見積書・請求書の出力形式: PDF保存のみとする(印刷は依頼者ご本人がPDFを開いて行う運用とし、アプリ側に印刷機能は設けない)。
- バックアップ: 手動エクスポート方式とし、エクスポートしたデータからの復元も可能な構成とする。起動エラー画面からの復元導線(★R1)はイテレーション2で追加済みである。イテレーション3では、バックアップ・復元のメモリ使用量を改善する(6章参照)。
- 取引先の氏名・連絡先や金銭に関する情報に加え、見積書・請求書には依頼者ご自身の事業者情報(氏名・屋号、住所)や振込先口座情報も記載されるため、これらの取り扱いにも十分留意する。

## 6. 今回のイテレーションの位置づけと対象スコープの概要

イテレーション3は、イテレーション総括.md(v3.0)7章で「先頭」とされた★T3⑤/SEC-16(バックアップ・復元のメモリ使用量の改善)と、優先度Aの案件管理を主対象とする。イテレーション2(入出金・経費の記録+★N1・★N2)は完了しており、番号は継続してイテレーション3とする。

今回の対象として、次を含む(2026-10-06のスコープ確認結果による)。
- ★T3⑤/SEC-16: バックアップ・復元のメモリ使用量の改善。ファイル全体を一度にメモリへ読み込む方式から、1件ずつ読み書きする方式(ストリーミング)へ見直す。復元ファイルの上限1GiBは維持する
- ★T4: 旧形式ZIP(領収書機能のない版で作成したもの)を復元すると現在の領収書がすべて消える点について、復元前に画面上の警告を追加する
- 案件管理(優先度A): 見積書・請求書、および入出金・経費の2種を案件に紐づけられるようにする。取引先は、案件の「取引先」項目(任意)で指定するだけとし、取引先の側から案件に紐づける機能は設けない(要件定義での★24の決定による)。案件ごとの収支集計(売上・経費・差引)を含める
- SEC-17: `npm audit fix`により、開発用の間接依存の脆弱性を解消する(更新後に`npm audit`・`npm test`・`.dmg`の再ビルドを確認する)

一方、次の項目は今回のスコープ外とし、次回以降のイテレーションへ持ち越す。
- B タスク・期限管理
- C セキュリティ・配布の強化のうちSEC-04(Electron Fuses・署名)、SEC-05(暗号化)、SEC-06(未署名配布)、pre-commit(gitleaks等)の導入(SEC-17を除く)
- D 品質改善: レビュー参考R-01〜R-22の未対応分(R-04を含む)、★D2(Node.jsバージョンの完全一致)、参考O3・O4、★R5(E2Eの断続的な失敗)
- SEC-08の残存分・SEC-13の残存分(過去のGit履歴に残るパス・メールアドレス。リスク受容を継続)、SEC-14(証拠画像の一時フォルダパス。証拠の改変になるため現状維持)
- ★D3の運用分(既存の取引先へのフリガナ入力)は、依頼者ご本人の入力による対応とする

なお、「自社情報」の名称は変更しない(依頼者ご本人のご意向。イテレーション1から継続)。

詳細な機能範囲の線引き(案件の項目、見積書・請求書および入出金・経費の紐づけの必須・任意、既存データの扱い、案件の状態管理の要否、収支集計の切り口・期間指定、旧形式ZIPの警告の表示条件等)は、次フェーズのplannerが作成するプロジェクト計画書にて確定する。

## 7. 要確認事項・未解決事項

- ★14(持ち越し課題の対応要否・着手時期)・★16(次イテレーションのスコープ・優先順位)は、今回のスコープ確認(2026-10-06)で確定したため、解消済みとする。★7・★8はイテレーション1で解消済みである。
- 案件管理に関する詳細(案件の項目・状態、見積書・請求書および入出金・経費との紐づけの必須・任意、既存データの扱い、収支集計の切り口・期間指定、紐づけが電子帳簿保存法の検索・改変検知に与える影響等)は、plannerの計画書および設計フェーズ(architecture)にて確定する。
- バックアップ・復元のストリーミング方式の実装詳細(復元ファイルの上限1GiBの検証方法を含む)、および旧形式ZIP復元時の警告の表示条件・文言は、plannerの計画書および設計フェーズ(architecture)にて確定する。
- タスク・期限管理(B)、SEC-04〜SEC-06・pre-commit(C)、品質改善(D)等の持ち越し項目は、次回以降のiteration-startで改めて確認する。
