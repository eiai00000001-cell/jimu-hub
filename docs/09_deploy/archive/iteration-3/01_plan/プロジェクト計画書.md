## 2. 案件概要

### 2.1 クライアント情報

- 依頼者: 個人事業主の方(ご本人が唯一の利用者)(プロジェクト概要.md 2章・3章)

### 2.2 依頼の背景・経緯

- 見積書・請求書の作成、入出金・経費の記録、取引先・案件の管理、タスク・期限の管理といった日々の事務作業を、一つのツールに集約して効率的に管理したいとのご要望(プロジェクト概要.md 2章)
- 現在これらを管理している既存ツールは無く、新規構築となる。既存データの移行は発生しない(プロジェクト概要.md 2章)

## 3. 目指すゴール

### 3.1 事務HUB全体のゴール

- 個人事業の事務作業(見積・請求、入出金・経費、取引先・案件、タスク・期限)を、PC上の一つのアプリで管理できる状態にする
- インボイス制度・電子帳簿保存法に配慮した記録・保存ができる状態にする(プロジェクト概要.md 5章)

### 3.2 過去イテレーションのゴール(参考)

- イテレーション0: アプリ基盤+取引先管理(達成済み。イテレーション総括.md v1.0)
- イテレーション1: 見積書・請求書の作成・PDF保存、入金ステータス管理、自社情報設定、源泉徴収計算、残課題対応(達成済み。イテレーション総括.md v2.0)
- イテレーション2: 入出金・経費の記録(勘定科目・領収書添付・集計・CSV出力・電帳法対応)、★N1(取引先の復帰)、★N2(下書き削除)(達成済み。イテレーション総括.md v3.0)

### 3.3 イテレーション3のゴール

- バックアップ・復元の際に、ファイル全体を一度にメモリへ読み込まず、1件ずつ読み書きする方式にして、メモリ使用量を抑えた状態にする。復元ファイルの上限1GiBは維持する(★T3⑤/SEC-16。プロジェクト概要.md 6章)
- 旧形式ZIP(領収書機能のない版で作成したもの)を復元しようとした際に、現在の領収書が消える旨を復元前に画面上でお知らせし、同意された場合のみ復元できる状態にする(★T4。プロジェクト概要.md 6章)
- 見積書/請求書・入出金/経費を案件に紐づけられ(取引先は案件の項目として指定する)、案件ごとの収支(売上・経費・差引)を確認できる状態にする(プロジェクト概要.md 6章)
- 案件への紐づけによって、電子帳簿保存法の水準(改変検知、日付・金額・取引先での検索)を損なわない状態にする(プロジェクト概要.md 5章)
- 開発用の間接依存の脆弱性(SEC-17)を解消し、更新後に`npm audit`・`npm test`・`.dmg`の再ビルドが問題ないことを確認した状態にする(プロジェクト概要.md 6章)

## 5. やること/やらないこと

詳細な機能要件は、要件定義フェーズ(analyst)にて要件定義書で確定する。

### 5.1 今回のイテレーションで扱うこと

プロジェクト概要.md 6章の対象を、今回のイテレーションで完了させる方針とする。ただし、案件管理(②③)の量が大きい場合は、③案件別集計の次回持ち越しを含め、project-leaderを通じて依頼者ご本人にご相談する(8章参照)。

- ★T3⑤/SEC-16: バックアップ・復元のメモリ使用量の改善(プロジェクト概要.md 6章)
  - ファイル全体を一度にメモリへ読み込む方式から、1件ずつ読み書きする方式(ストリーミング)へ見直す
  - 復元ファイルの上限1GiBは維持する。具体的な方式・検証方法は設計で確定する
- ★T4: 旧形式ZIP復元時の警告(プロジェクト概要.md 6章)
  - 表示条件: 選択したZIPに領収書が含まれず、かつ現在の領収書が1件以上ある場合のみ警告する
  - 警告で領収書が消える旨をお知らせし、同意された後に復元を実行する。同意されない場合は復元を中止する(データは変更しない)。文言は要件定義で確定する
- 案件管理(プロジェクト概要.md 6章)
  - 案件の項目: 案件名、取引先(任意)、期間(開始日・終了日。ともに任意)、メモ
  - 案件の状態: 「進行中」「完了」の2値。完了の案件は一覧で絞り込め、紐づけの候補からは除外する
  - 紐づけ対象: 見積書・請求書、入出金・経費の2種。いずれも任意で、1件につき案件は1つまで。後から付け替えられる
  - 取引先: 案件の「取引先」項目(任意)で指定するのみとし、取引先の側から案件に紐づける機能は設けない(★24。要件定義でご決定)
  - 見積書・請求書の紐づけ: 書類本体とは別に管理し、発行(PDF保存)後も付け替えられる。付け替えの変更履歴を残す。書類の改変検知・検索条件には影響させない
  - 既存データ(イテレーション1・2で作成した取引先・書類・入出金・経費): 「案件なし」のまま移行し、後から個別に紐づける
  - 案件ごとの収支集計: 案件単位で売上・経費・差引を表示する。期間は案件の全期間のみ(日付範囲での絞り込みは設けない)。売上は発行済み請求書の金額とし、見積書は含めない
  - 電子帳簿保存法対応: 紐づけによって発行済み書類・記録の改変検知や、日付・金額・取引先での検索に影響を与えない(プロジェクト概要.md 5章)
- SEC-17: `npm audit fix`による開発用の間接依存の脆弱性の解消(更新後に`npm audit`・`npm test`・`.dmg`の再ビルドを確認する)

#### 他機能との連携範囲(今回確定分)

- 取引先管理: 案件の任意項目として取引先を指定できる。取引先の側から案件への紐づけ機能は設けない
- 見積書・請求書: 案件に紐づける(任意・付け替え可)。案件別収支の売上は発行済み請求書の金額を対象とする
- 入出金・経費: 案件に紐づける(任意・付け替え可)。案件別収支の経費の対象とする
- バックアップ・復元: 案件データ・紐づけ情報もエクスポート・復元の対象に含める。ストリーミング化と案件データの追加を両立させる(設計で確認)
- 電子帳簿保存法対応: イテレーション1・2の水準を維持する

## 7. リスク・懸念事項

- 復元処理の改修によるデータ損失: ストリーミング化はバックアップ・復元の中核部分の改修であり、復元に失敗すると既存データを失うおそれがある。復元失敗時に元のデータへ戻せること、大きなファイルでの動作を、テストで重点的に確認する。先頭で着手し、後続への影響を早期に把握する
- 旧形式ZIP警告の取りこぼし: 警告の表示条件に漏れがあると、依頼者が気づかないまま領収書を失うおそれがある。要件定義で条件・文言を明確にし、テストで確認する
- 既存DBへの影響: 案件への紐づけ追加に伴うDB変更(既存データの「案件なし」での移行)で、既存の取引先・書類・入出金・経費・領収書に不整合が生じるおそれがある。設計で移行方式を確認し、テストで確認する
- 電帳法水準の維持: 発行後の書類を付け替え可とするため、紐づけが書類本体の改変検知・検索条件に影響しない構成が必須となる。設計・レビュー・テストで重点確認する
- 機能範囲の大きさ: ①〜④に加え案件管理は紐づけ対象が2種(書類、入出金・経費)あるため、工数が膨らむおそれがある。依存関係の順(①→④→②→③)で進め、必要なら③の持ち越しを依頼者ご本人にご相談する
- 収支集計の解釈: 売上を発行済み請求書の金額、経費を入出金・経費の記録とするため、入金済みかどうかや取消記録の扱いで数値が実態とずれて見えるおそれがある。要件定義で集計対象を明確にする(8章★19参照)
- 依存関係更新の影響(SEC-17): `npm audit fix`により、ビルドやテストに影響が出るおそれがある。更新後に`npm audit`・`npm test`・`.dmg`再ビルドで確認する
