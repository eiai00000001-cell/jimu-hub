- 作成日: 2026-09-28
- 版数: v4.1

## 2. プロジェクトの目的・背景

「事務HUB」は、個人事業主である依頼者ご本人が日々行う事務作業を一つのツールに集約し、効率的に管理できるようにすることを目的として開発する。対象とする業務は、見積書・請求書の作成、入出金・経費の記録、取引先・案件の管理、タスク・期限の管理である。現時点でこれらの業務を管理している既存ツールは無く、今回新規に構築するものであり、既存システムからのデータ移行は発生しない。

## 3. 対象ユーザー・利用シーン

- 利用者: 依頼者ご本人のみ(唯一の利用者であり、複数ユーザーでの利用は想定しない)
- 利用端末: PCを中心とする
- 想定利用シーン: 見積書・請求書の作成、日々の入出金・経費の記録、取引先や案件情報の参照・更新、タスクや期限の管理など、個人事業の運営に伴う事務作業全般

## 4. 技術スタック・制約(初回確定分)

- 提供形態: インターネットには公開せず、ローカル環境のみで動作するデスクトップアプリケーションとする。
- 認証: 認証機能は設けない方針とする。PC自体のログイン・画面ロックによって保護することとする。ヒアリング当初は「ログイン必須」案も挙がったが、ローカル専用のデスクトップアプリであるという特性を踏まえ、「認証なし」に決定した。
- 具体的な使用言語・フレームワーク・データベース等の技術選定は、イテレーション0の設計フェーズ(基本設計書.md・詳細設計書.md)にて確定済みであり、イテレーション1以降はこれを前提として踏襲する。イテレーション1のPDF出力機能の技術要素も確定済みであり、同様に踏襲する。イテレーション2の技術要素(領収書ファイルの保存方式、CSV出力の形式・文字コード等)も確定済みであり、同様に踏襲する。イテレーション3の技術要素(バックアップ・復元のストリーミング方式、案件と各データの紐づけ方式等)も確定済みであり、同様に踏襲する。イテレーション4で新たに必要となる技術要素(タスクのデータ構造、タスクと案件の任意の紐づけ方式、pre-commit〔gitleaks+独自ルール〕の仕組み等)の選定は、設計フェーズ(architecture)にて確定する。
- デザイン担当: designer(業務用のデスクトップツールであり、デザイン重視の制作案件ではないため。イテレーション1〜3の実績を継続する)。

## 5. セキュリティ・法令面の方針

- インボイス制度(適格請求書等保存方式)への対応: イテレーション総括.md(v1.0)で申し送られていた依頼者のインボイス登録状況(★7)について、イテレーション1のスコープ確認で「登録・未登録の両方に対応する」方針が確定した。設定画面にインボイス登録番号を入力した場合にのみ、見積書・請求書に適格請求書等保存方式の記載事項(登録番号等)を表示する。登録番号が未入力の場合は、区分記載請求書等の形式で出力する。
- 電子帳簿保存法への対応: ★8について、最小限の対応水準として「発行した見積書・請求書等の文書を改変せずに保存し、日付・金額・取引先の各条件で検索できるようにする」方針が確定した(イテレーション1で実装済み)。イテレーション2では、この水準(改変検知、日付・金額・取引先での検索)を入出金・経費の記録にも適用し、添付する領収書ファイル(PDF・画像)も同水準で扱った。イテレーション3で見積書・請求書・入出金・経費を案件に紐づける際も、この水準を損なわない(紐づけによって、発行済み書類の改変検知や検索条件に影響を与えない)ことを前提とした(実装済み)。イテレーション4でタスクを扱う際も、既存の発行済み書類・記録の改変検知や検索条件に影響を与えないことを前提とする。詳細は設計フェーズで確定する。
- 見積書・請求書の出力形式: PDF保存のみとする(印刷は依頼者ご本人がPDFを開いて行う運用とし、アプリ側に印刷機能は設けない)。
- バックアップ: 手動エクスポート方式とし、エクスポートしたデータからの復元も可能な構成とする。起動エラー画面からの復元導線(★R1)はイテレーション2で追加済みである。イテレーション3でバックアップ・復元のメモリ使用量を改善済みである。
- 開発時の情報混入対策: 作成者情報・一時フォルダのパス・秘密情報の混入を自動で検査する仕組みとして、pre-commit(gitleaks+独自ルール)をイテレーション4で導入する(6章参照)。
- 取引先の氏名・連絡先や金銭に関する情報に加え、見積書・請求書には依頼者ご自身の事業者情報(氏名・屋号、住所)や振込先口座情報も記載されるため、これらの取り扱いにも十分留意する。

## 6. 今回のイテレーションの位置づけと対象スコープの概要

イテレーション4は、イテレーション総括.md(v4.0)7章の推奨に沿い、残る主要機能であるB タスク・期限管理を主対象とし、前回の積み残しを閉じる保守作業と、pre-commitの導入を併せて行う。イテレーション3(案件管理+バックアップ・復元のメモリ使用量改善)は完了しており、番号は継続してイテレーション4とする(本案件は0始まり)。

イテレーション3の完了条件であった依頼者ご本人のMacでの実機確認4項目(TC-128〜TC-131。★T2(i3))は、依頼者ご本人により実施済みで、問題がないことをご確認いただいた(2026-10-13)。これによりイテレーション3の完了条件は満たされ、★T2(i3)は解消扱いとする。納品書.md 7.4章への結果追記は、納品フェーズ等で対応する。

今回の対象として、次を含む(2026-10-13のスコープ確認結果による)。
- 保守作業(前回の積み残しの解消)
  - SEC-17: 開発者側Macの`app/`で`npm ci`により`node_modules`を入れ直し、`npm test`と`.dmg`の作成を確認する
  - SEC-19: 開発者側Macの一時フォルダに残るテスト・確認作業の残骸を削除する(削除は、事前にユーザーの許可を得て行う)
  - ★T3(i3): 設計書へ、案件の画面のタイトルバー表記を追記する
- B タスク・期限管理(主対象): サイドメニューで準備中のままの「タスク・期限」を実装する。タスクは単独でも登録でき、必要に応じて案件に任意で紐づけられるものとする
- pre-commit(gitleaks+独自ルール)の導入: 作成者情報・一時フォルダのパス・秘密情報の混入を自動で検査する仕組みを導入する。あわせて、SEC-18・SEC-19の再発防止(E2Eの作業フォルダの場所、テスト後の後片付け)も扱ってよいものとする

一方、次の項目は今回のスコープ外とし、次回以降のイテレーションへ持ち越す。
- D 品質改善: レビュー参考R-01〜R-28の未対応分(R-04、R-23〜R-25等を含む)、★D2(Node.jsバージョンの完全一致)、参考O3・O4、★R5(E2Eの断続的な失敗)
- C セキュリティ・配布の強化のうち、SEC-04(Electron Fuses・署名)、SEC-05(暗号化)、SEC-06(未署名配布)
- SEC-20・★F3(`electron-builder` 27系の正式版待ち)
- SEC-08の残存分・SEC-13の残存分(過去のGit履歴に残るパス・メールアドレス。リスク受容を継続)、SEC-14・SEC-18(証拠画像の一時フォルダパス。証拠の改変になるため現状維持)
- ★D3の運用分(既存の取引先へのフリガナ入力)は、依頼者ご本人の入力による対応とする

なお、「自社情報」の名称は変更しない(依頼者ご本人のご意向。イテレーション1から継続)。

詳細な機能範囲の線引き(タスクの項目・状態管理の要否、期限の扱い〔通知・リマインドの要否を含む〕、案件への紐づけの操作と表示、一覧・検索の切り口、pre-commitの検査対象と独自ルールの内容等)は、次フェーズのplannerが作成するプロジェクト計画書にて確定する。

## 7. 要確認事項・未解決事項

- ★T2(i3)(実機確認4項目)は、依頼者ご本人による実施済み・問題なし(2026-10-13)のため、解消済みとする。納品書.md 7.4章への結果追記は、納品フェーズ等で対応する(申し送り)。
- 請求書の支払期限・見積書の有効期限等とタスク・期限管理との連携の要否・範囲は、要件定義(analyst)で決める。
- タスクの詳細(項目・状態、期限の扱い、案件への任意の紐づけの仕様、一覧・検索の切り口等)は、plannerの計画書、要件定義(analyst)および設計フェーズ(architecture)にて確定する。タスクが電子帳簿保存法の検索・改変検知に影響しないことの確認も、設計フェーズで行う。
- pre-commit(gitleaks+独自ルール)の検査対象・独自ルールの内容、およびSEC-18・SEC-19の再発防止策(E2Eの作業フォルダの場所、テスト後の後片付け)の具体策は、plannerの計画書および設計フェーズ(architecture)にて確定する。
- SEC-19の残骸の削除は、実施前に必ずユーザーの許可を得る。
- SEC-04〜SEC-06・SEC-20、品質改善(D)等の持ち越し項目は、次回以降のiteration-startで改めて確認する(SEC-04〜SEC-06は、Apple Developer Programへの登録の要否を含めて別途ご検討いただく)。
