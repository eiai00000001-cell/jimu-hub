- 作成日: 2026-09-26
- 版数: v1.0

## 2. 案件概要

### 2.1 クライアント情報

- 依頼者: 個人事業主の方(ご本人が唯一の利用者)(プロジェクト概要.md 2章・3章)

### 2.2 依頼の背景・経緯

- 見積書・請求書の作成、入出金・経費の記録、取引先・案件の管理、タスク・期限の管理といった日々の事務作業を、一つのツールに集約して効率的に管理したいとのご要望(プロジェクト概要.md 2章)
- 現在これらを管理している既存ツールは無く、新規構築となる。既存データの移行は発生しない(プロジェクト概要.md 2章)

## 3. 目指すゴール

### 3.1 事務HUB全体のゴール

- 個人事業の事務作業(見積・請求、入出金・経費、取引先・案件、タスク・期限)を、PC上の一つのアプリで管理できる状態にする
- インボイス制度・電子帳簿保存法に配慮した記録・保存ができる状態にする(プロジェクト概要.md 5章)

### 3.2 イテレーション0のゴール

- 以降の機能を載せていく土台となる「アプリ基盤」が整っている
  - ローカル環境で動作するデスクトップアプリとしての骨格
  - データの保存方式
  - 手動エクスポートによるバックアップと、エクスポートデータからの復元
- 「取引先管理」機能により、取引先情報の登録・参照・更新ができる

## 4. 進め方

### 4.1 全体の進め方

- 案件概要→計画→要件定義→設計→デザイン→実装→レビュー→テスト→セキュリティ→納品→総括の11フェーズで進める
- 初回(イテレーション0)はウォーターフォールで一気通貫に進め、以降の機能追加はアジャイル的に同じ11フェーズをループする
- 計画→要件定義、要件定義→設計、設計→デザイン、デザイン→実装、セキュリティ→納品の各境界では、成果物をご確認いただき、進行のご指示をいただいてから次フェーズへ進む

### 4.2 各フェーズで確定させること(イテレーション0)

| フェーズ | 確定させること |
|---|---|
| 計画 | 目的・ゴール、やること/やらないこと、取引先管理と他機能の連携範囲の線引き(本書) |
| 要件定義 | アプリ基盤・取引先管理の機能要件、取引先の管理項目、非機能要件(バックアップ・復元、個人情報の扱い等) |
| 設計 | 技術選定(言語・フレームワーク・データベース)、データの保存形式・保存場所、エクスポートのファイル形式・操作手順、画面仕様、以降の機能追加に耐えるデータ構造 |
| デザイン | 配色・雰囲気等の方向性、画面モックアップ |
| 実装 | テスト先行(TDD)による実装 |
| レビュー・テスト | 設計書との整合確認、実機・シナリオテスト |
| セキュリティ | ローカル保存データ・エクスポートファイルの取り扱い等の静的チェック |
| 納品 | 利用環境へのインストール、操作マニュアル |
| 総括 | 完了判定と次イテレーション候補の整理 |

### 4.3 スケジュール感

- 稼働時期の期限は特に設けず、順次進める(プロジェクト概要.md 6章)

### 4.4 以降のイテレーションの想定(当たり)

以下は現時点の候補であり、順序・範囲は各イテレーション着手時に確定する。

| 想定 | 対象機能 |
|---|---|
| イテレーション0 | アプリ基盤+取引先管理(今回) |
| イテレーション1以降 | 案件管理、見積書・請求書の作成、入出金・経費の記録、タスク・期限管理(順不同・順次対応) |

## 5. やること/やらないこと

詳細な機能要件は、要件定義フェーズ(analyst)にて要件定義書で確定する。

### 5.1 今回のイテレーションで扱うこと

- アプリ基盤
  - ローカル環境のみで動作するデスクトップアプリとしての骨格(PC利用が中心)
  - データの保存方式(具体的な形式・場所は設計フェーズで確定)
  - 手動エクスポートによるバックアップ、エクスポートデータからの復元
  - 以降の機能(案件・見積請求・入出金経費・タスク)を追加していける画面・データの構成
- 取引先管理
  - 取引先情報の登録・一覧表示・参照・更新・削除
  - 取引先の管理項目の定義(具体的な項目は要件定義フェーズで確定)
  - 以降の機能から参照される「取引先マスタ」としての整備(下記5.3参照)

### 5.2 やらないこと・対象外・将来検討

- 認証(ログイン)機能: 設けない。PCのログイン・画面ロックで保護する(プロジェクト概要.md 4章)
- 複数ユーザーでの利用(プロジェクト概要.md 3章)
- インターネット公開・クラウド同期(プロジェクト概要.md 4章)
- 既存データの移行(プロジェクト概要.md 2章)
- 案件管理、見積書・請求書の作成、入出金・経費の記録、タスク・期限管理: 以降のイテレーションで対応
- 自動バックアップ(今回は手動エクスポート方式のみ)

### 5.3 取引先管理と以降の機能との連携範囲の線引き

| 項目 | イテレーション0(今回) | 以降のイテレーション |
|---|---|---|
| 取引先の基本情報(名称・連絡先等) | 取引先管理で登録・更新する | 各機能は取引先を選択して参照する(同じ情報を各機能で重複登録しない) |
| 取引先を一意に識別する仕組み | 設計に含める(他機能から参照できる形) | 案件・見積請求・入出金経費・タスクがこれを参照する |
| 取引先ごとの案件・請求・入出金の一覧や集計 | 対象外 | 各機能の追加時に、取引先詳細画面への表示等を検討する |
| 参照されている取引先の削除時の扱い | 削除方式(完全削除/利用停止等)の方針のみ要件定義で決める | 他機能から参照される状態での挙動を各機能追加時に確定する |
| 見積書・請求書に記載する取引先情報 | 記載に必要となりそうな項目(宛名・住所等)を管理項目の候補として検討する | 見積・請求機能の追加時に過不足を見直す |
| 依頼者ご自身の事業者情報(屋号・インボイス登録番号等) | 対象外(取引先とは別に扱う) | 見積・請求機能の追加時に扱う |

- 基本方針: 取引先は「各機能から参照される共通の台帳」とし、今回は台帳そのものの整備に留める。他機能側の連携実装は、その機能を扱うイテレーションで行う。

## 6. 前提・制約

- 利用者: 依頼者ご本人のみ(プロジェクト概要.md 3章)
- 利用端末: PCを中心とする(プロジェクト概要.md 3章)
- 提供形態: ローカル環境のみで動作するデスクトップアプリ(プロジェクト概要.md 4章)
- 認証: 設けない(プロジェクト概要.md 4章)
- 技術選定: 設計フェーズで確定する(プロジェクト概要.md 4章)
- 法令: インボイス制度・電子帳簿保存法への配慮(プロジェクト概要.md 5章)
- 納期: 特に期限を設けない(プロジェクト概要.md 6章)
- 予算・体制: プロジェクト概要.mdに記載なし

## 7. リスク・懸念事項

- データ消失: ローカル保存のみで自動バックアップが無いため、PCの故障等でデータを失うおそれがある。エクスポートの操作を分かりやすくし、定期的な実施を促す工夫を要件定義・設計で検討する
- 個人情報・機微情報の保護: 認証が無く、アプリ内のデータはPCのログイン・画面ロックのみで保護される。また、エクスポートファイルがPC外に持ち出される可能性がある。保存データ・エクスポートファイルの取り扱いを設計・セキュリティフェーズで確認する
- 後続機能の追加に伴う手戻り: 取引先のデータ構造が後続機能(特に見積・請求)の要件に合わないと改修が必要になる。今回の設計で拡張しやすい構造にしておく
- 法令対応の範囲: 電子帳簿保存法の対応範囲(どの記録・書類をどう保存するか)が今回未確定であり、見積・請求、入出金・経費の機能追加時に影響が大きい
- 復元時のデータ整合: 以降のイテレーションでデータ構造が変わると、古いエクスポートデータを復元できなくなるおそれがある。バージョン差の扱いを設計で考慮する
