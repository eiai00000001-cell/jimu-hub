## 2. 案件概要

### 2.1 クライアント情報

- 依頼者: 個人事業主の方(ご本人が唯一の利用者)(プロジェクト概要.md 2章・3章)

### 2.2 依頼の背景・経緯

- 見積書・請求書の作成、入出金・経費の記録、取引先・案件の管理、タスク・期限の管理といった日々の事務作業を、一つのツールに集約して効率的に管理したいとのご要望(プロジェクト概要.md 2章)
- 現在これらを管理している既存ツールは無く、新規構築となる。既存データの移行は発生しない(プロジェクト概要.md 2章)

## 3. 目指すゴール

### 3.1 事務HUB全体のゴール

- 個人事業の事務作業(見積・請求、入出金・経費、取引先・案件、タスク・期限)を、PC上の一つのアプリで管理できる状態にする
- インボイス制度・電子帳簿保存法に配慮した記録・保存ができる状態にする(プロジェクト概要.md 5章)

### 3.2 イテレーション1のゴール

イテレーション0のゴール(アプリ基盤+取引先管理)は達成済み(イテレーション総括.md v1.0参照)。イテレーション1では、次の状態を目指す。

- 見積書・請求書を作成し、PDFで保存できる状態にする(適格請求書等保存方式・区分記載請求書等の両対応、登録番号の入力有無で自動切替)(プロジェクト概要.md 6章)
- 見積書から請求書へ、ボタン一つで内容を引き継いで作成できる状態にする(プロジェクト概要.md 6章)
- 請求書の入金ステータス(未収/入金済み)を管理できる状態にする(プロジェクト概要.md 6章)
- 依頼者ご自身の事業者情報・振込先を設定でき、書類に反映できる状態にする(プロジェクト概要.md 6章)
- 源泉徴収税額を計算できる状態にする(プロジェクト概要.md 6章)
- イテレーション0からの残課題のうち、★R1(起動エラー画面の復元導線)・★D3(取引先フリガナ・五十音順表示)・SEC-07(不要同梱物の整理)・★D1(アプリアイコン制作)を解消した状態にする(プロジェクト概要.md 6章、イテレーション総括.md v1.0 6章)

## 4. 進め方

### 4.1 全体の進め方

- 案件概要→計画→要件定義→設計→デザイン→実装→レビュー→テスト→セキュリティ→納品→総括の11フェーズで進める
- 初回(イテレーション0)はウォーターフォールで一気通貫に進め、以降の機能追加はアジャイル的に同じ11フェーズをループする。イテレーション1は、このループの最初の適用例となる
- 計画→要件定義、要件定義→設計、設計→デザイン、デザイン→実装、セキュリティ→納品の各境界では、成果物をご確認いただき、進行のご指示をいただいてから次フェーズへ進む

### 4.2 各フェーズで確定させること(イテレーション1)

| フェーズ | 確定させること |
|---|---|
| 案件概要 | プロジェクト概要.md v1.1にて、対象スコープ・法令対応方針(インボイス・電帳法)を確定済み |
| 計画 | 目的・ゴール、やること/やらないこと、他機能(取引先管理・入出金経費・案件管理)との連携範囲の線引き、残課題対応の位置づけ(本書) |
| 要件定義 | 見積書・請求書の機能要件、取引先未登録の相手への対応方法(8章★10参照)、入金ステータス・源泉徴収の詳細仕様、残課題(★R1・★D3・SEC-07・★D1)の要件 |
| 設計 | PDFレイアウト(適格請求書等保存方式/区分記載請求書等)、電子帳簿保存法対応の保存・検索方式、見積書・請求書関連の画面仕様、★R1の復元導線設計 |
| デザイン | 見積書・請求書関連画面のモックアップ、★D1アプリアイコンのデザイン(同一フェーズでまとめて実施) |
| 実装 | テスト先行(TDD)による実装。SEC-07(同梱物整理)・★D3(フリガナ項目)をあわせて対応 |

| 納品 | 実機確認、操作マニュアルの更新 |
| 総括 | 完了判定と次イテレーション候補の整理 |

## 5. やること/やらないこと

詳細な機能要件は、要件定義フェーズ(analyst)にて要件定義書で確定する。

### 5.1 今回のイテレーションで扱うこと

- 見積書・請求書の作成・PDF保存(適格請求書等保存方式・区分記載請求書等の両対応、登録番号の入力有無で自動切替)(プロジェクト概要.md 6章)
- 見積書から請求書への変換(ボタン一つで見積書の内容を引き継いだ請求書を作成)(プロジェクト概要.md 6章)
- 請求書の入金ステータス管理(未収/入金済み。請求書側の独立項目として実装)(プロジェクト概要.md 6章)
- 自社情報・振込先の設定(氏名・屋号、住所、振込先口座など、書類に表示する事業者情報の設定画面)(プロジェクト概要.md 6章)
- 源泉徴収税額の計算(個人事業主向け)(プロジェクト概要.md 6章)
- 残課題対応(イテレーション総括.md v1.0 6章、プロジェクト概要.md 6章)
  - ★R1: 起動エラー画面(データベース破損時)に、エクスポートファイルを選択して復元する導線を追加する
  - ★D3: 取引先にフリガナ項目を追加し、一覧を五十音順で表示できるようにする
  - SEC-07: electron-builderの除外設定を見直し、配布物に含まれる不要な同梱ファイルを整理する
  - ★D1: アプリアイコンをゼロから制作する(見積書・請求書の画面デザインと同じデザインフェーズでまとめてヒアリング・制作する)

#### 他機能との連携範囲(今回確定分)

- 取引先管理: 見積書・請求書は、既存の取引先マスタから選択して作成する運用に統一する。取引先マスタに未登録の相手への発行可否・方法は、要件定義フェーズで確定する(8章★10参照)
- 入出金・経費: 入金ステータス(未収/入金済み)は請求書側の独立項目とし、入出金・経費機能とのデータ連携は行わない(次回以降の検討事項)
- 案件管理: 見積書・請求書は取引先のみに紐づけ、案件との紐づけは今回持たない。案件との紐づけは、案件管理機能の追加時にあらためて検討する
- 電子帳簿保存法対応: 今回は見積書・請求書のみを実装対象とする。入出金・経費等の他書類への拡張は次回以降に検討する

### 5.2 やらないこと・対象外・将来検討

- 認証(ログイン)機能、複数ユーザーでの利用、インターネット公開・クラウド同期、既存データの移行(プロジェクト概要.md 3・4章、承継)
- 入出金・経費の記録、案件管理、タスク・期限管理(イテレーション総括.md v1.0 7章の優先度B〜D。次回以降のイテレーションで対応)
- 見積書・請求書と案件管理・入出金経費との項目連携(上記5.1のとおり、今回は連携なし。次回以降検討)
- 取引先マスタに未登録の相手への発行方法の詳細(要件定義フェーズで確定。8章★10参照)
- SEC-04(Electron Fuses・署名)、SEC-05(暗号化)、SEC-06(未署名配布)(次回以降検討)
- ★D2(Node.jsバージョンの完全一致)、BUG-03(IPCエラーメッセージの文言、参考所見。対応不要)
- テストエビデンスの運用課題(結合シナリオ再実行時の証拠画像上書き)は、次回tester着手時に対応要否を判断する

### 5.3 タスクの大枠

案件概要〜総括の全フェーズを、今回のイテレーションでも実施する(4.2参照)。機能単位の実装タスクは次のとおり(残課題対応は個別チケットとして管理)。

- 見積書の作成・PDF保存
- 請求書の作成・PDF保存
- 見積書から請求書への変換
- 請求書の入金ステータス管理
- 自社情報・振込先の設定
- 源泉徴収税額の計算
- ★R1: 起動エラー画面への復元導線追加
- ★D3: 取引先のフリガナ項目追加・五十音順表示
- SEC-07: electron-builderの除外設定の見直し
- ★D1: アプリアイコンの制作・組み込み

主要機能を優先して進め、残課題は実装の合間・最後にまとめて対応する方針とする。詳細・状態はタスク管理表.md(docs/01_plan)を参照する。

## 6. 前提・制約

- 利用者: 依頼者ご本人のみ(プロジェクト概要.md 3章、承継)
- 利用端末: PCを中心とする(プロジェクト概要.md 3章、承継)
- 提供形態: ローカル環境のみで動作するデスクトップアプリ(プロジェクト概要.md 4章、承継)
- 認証: 設けない(プロジェクト概要.md 4章、承継)
- 技術スタック: イテレーション0で確定済みの技術選定を踏襲する。PDF出力等、新たに必要となる技術要素の選定は設計フェーズ(architecture)で確定する(プロジェクト概要.md 4章)
- インボイス制度対応: 登録・未登録の両方に対応し、設定画面の登録番号入力の有無で表示内容を自動切替する(プロジェクト概要.md 5章)
- 電子帳簿保存法対応: 発行した見積書・請求書を改変せず保存し、日付・金額・取引先の各条件で検索できるようにする。今回は見積書・請求書のみを対象とする(プロジェクト概要.md 5章、本書5.1)
- 出力形式: PDF保存のみとし、印刷機能はアプリ側に設けない(プロジェクト概要.md 5章)
- バックアップ: 手動エクスポート方式。★R1(起動エラー画面からの復元導線)を今回追加する(プロジェクト概要.md 5章)
- 納期: 特に期限を設けない(プロジェクト概要.md 6章、承継)
- 予算・体制: プロジェクト概要.mdに記載なし(承継)

## 7. リスク・懸念事項

- 法令対応の誤り: インボイス制度・電子帳簿保存法への対応に誤りがあると、依頼者の実務(税務処理等)に影響するおそれがある。設計・実装・レビューの各段階で、法令面の記載事項との整合を確認する
- PDFレイアウトの手戻り: 適格請求書等保存方式・区分記載請求書等、それぞれの記載事項の整理が不十分だと、デザイン・実装フェーズで手戻りが発生するおそれがある。設計フェーズで記載事項を明確化する
- 取引先マスタ未登録の相手への対応: 見積書・請求書は取引先マスタからの選択に統一する方針としたため、未登録の相手には事前の取引先登録操作が必要になる。運用上の手間について、要件定義フェーズで依頼者に確認する(8章★10参照)
- 主要機能と残課題の並行実施: 主要機能(見積書・請求書関連)と残課題(★R1・★D3・SEC-07・★D1)を同一イテレーションで扱うため、優先順位を誤ると主要機能のスケジュールに影響するおそれがある。4.4・5.3の着手順序方針(主要機能優先)に沿って進める
- 後続機能の追加に伴う手戻り: 見積書・請求書のデータ構造が、次回以降の入出金・経費/案件管理機能の要件に合わないと改修が必要になる。設計フェーズで、過度に将来を制約しない拡張しやすい構造としておく
