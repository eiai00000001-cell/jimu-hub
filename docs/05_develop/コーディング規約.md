- 版数: v1.0

## 2. 前提

事務HUBは、Electron + TypeScript + React + SQLite(better-sqlite3 + Drizzle ORM)構成のMac専用デスクトップアプリケーションである。本規約は、実装コードを置く`app/`フォルダ内で一貫させるルールをまとめたものであり、以降のイテレーションで機能を追加する際も本規約に従う。追加・変更があれば本ファイルを改訂する。

## 3. ディレクトリ構成

案件フォルダ直下に、Electronアプリ一式をまとめた単一フォルダ`app/`を作成する。Main(業務ロジック・DBアクセス)・Preload・Renderer(画面)は最終的に`electron-builder`で1つの配布物にまとめるため、`backend/`・`frontend/`のように分けず、1つのnpmパッケージとして管理する。

```
app/
  src/
    main/         … Mainプロセス
      db/           DB接続初期化(db.ts)・Drizzleスキーマ(schema.ts)
      repositories/ Repository層(テーブルへのCRUD)
      services/     Application Service層(業務ロジック)
      ipc/          IPCハンドラ層(`clients:*`・`data:*`・`app:*`チャンネル)
      dev/          開発用CLI(サンプルデータ投入スクリプト等。配布物には含めない)
      index.ts      アプリのエントリーポイント
    preload/      … contextBridgeで公開するAPI定義(index.ts)
    renderer/     … Reactアプリ
      index.html
      src/
        components/ 画面共通部品(ボタン・入力欄・メッセージ・バッジ等)
        layout/     サイドバー・共通レイアウト
        pages/      画面単位のコンポーネント
        styles/     共通スタイルシート(global.css)
        types/      Renderer固有の型定義(window.jimuhubApi等)
        App.tsx     画面遷移(ルーティング)
        main.tsx    エントリーポイント
    shared/       … Main/Renderer共通(Zodスキーマ・型定義・IPCチャンネル名・メッセージ文言)
  e2e/          … Playwright E2Eテスト(fixtures/・tests/)
  drizzle等の設定ファイルは今後DBマイグレーションを追加する際に必要に応じて配置する
```

各層のテストコードは、対象ファイルと同じディレクトリに`*.test.ts`(または`*.test.tsx`)として配置する(Vitestの一般的な配置慣習)。

## 4. 命名規則

| 対象 | 規則 | 例 |
|---|---|---|
| Reactコンポーネントファイル | `PascalCase.tsx` | `ClientListPage.tsx` |
| コンポーネント以外のTS/JSファイル | `kebab-case.ts` | `client.repository.ts`、`db.ts` |
| クラス名・型名・コンポーネント名 | `PascalCase` | `ClientService`、`Client` |
| 関数名・変数名 | `camelCase` | `listClients`、`activeClientCount` |
| 定数(値を変更しない設定値等) | `UPPER_SNAKE_CASE` | `CURRENT_SCHEMA_VERSION` |
| DBカラム名 | `snake_case`(詳細設計書6章のDDLに準拠) | `contact_person` |
| IPCチャンネル名 | `対象:操作`のkebab-case(詳細設計書7章に準拠) | `clients:list`、`data:export` |
| 機能ID | 詳細設計書のF-01〜F-08表記をコード内コメント・テスト説明文に用いる | `[F-05]取引先一覧画面` |

## 5. TypeScript・React共通ルール

- `strict: true`を前提とし、`any`は原則使用しない(やむを得ない場合はコメントで理由を明記)。
- Main/Renderer間でやり取りする型(取引先・IPCリクエスト/レスポンス等)は`src/shared/`に置き、双方から同じ定義を参照する(型の二重定義を避ける)。
- Reactコンポーネントの戻り値型は`ReactElement`を明示する(`@types/react` 19系ではグローバルな`JSX`名前空間を直接参照できないため)。
- コンポーネントはpropsに関数・状態を受け取り、Main側の呼び出し(`window.jimuhubApi.*`)は各ページコンポーネント内で直接行う(小規模アプリのため、状態管理ライブラリは導入しない)。
- 画面遷移は`react-router`等を追加せず、`App.tsx`内の軽量なstateベースのルーティング(`Route`判別共用体 + `useState`)で管理する(画面数が少なく、URLベースの深いリンクが不要なため)。

## 6. コメント方針

- 各クラス・コンポーネント・主要関数の先頭に、対応する詳細設計書の章番号・機能ID(例: `[F-05]`)を日本語コメントで記載し、設計書とコードを相互参照できるようにする。
- 自明な処理(単純な代入・単純なgetter等)にはコメントを付けない。複雑な条件分岐・設計上の理由がある実装(例: E2Eテスト専用の分岐)にのみ理由を記載する。
- コメントの言語は日本語を基本とする(コメント以外の識別子は英語)。

## 7. Lint・フォーマット

- ESLint(`typescript-eslint`推奨ルール + `eslint-plugin-react-hooks` + `eslint-plugin-react-refresh`) + Prettierを使用する。
- 実行コマンド: `npm run lint` / `npm run lint:fix` / `npm run format` / `npm run format:check`
- Prettier設定: セミコロンなし・シングルクォート・印字幅100・末尾カンマなし(`.prettierrc.json`参照)。
- pre-commitフック(husky等)は導入しない(個人開発規模のため、`npm run lint`・`npm run test`を実装完了時に手動実行する運用とする)。

## 8. テスト方針(TDD)

- 開発手順はRed(失敗するテストを書く)→Green(最小実装で通す)→Refactor(整理する)を基本とする。
- テストツール: Vitest(Main層のRepository・Service・共通スキーマの単体テスト、Renderer層のコンポーネント/画面テスト) + React Testing Library(画面の主要な操作の検証)。
- テスト範囲の方針(ユーザー確認済み): データの保存・検索・更新・削除等の「裏側の処理」に加え、画面の主要な操作(入力して登録する、検索して絞り込む、確認ダイアログで実行する等)も自動テストにする。表示のみで操作を伴わない末端の部品(ボタン・バッジ等の見た目)は、ページ単位のテストで間接的に確認し、個別の単体テストは必須としない。
- Main層のテストは`vitest.config.ts`の既定環境(`node`)で実行し、Renderer層のテストはファイル冒頭に`// @vitest-environment jsdom`を付けて`jsdom`環境で実行する。
- 実行コマンド: `npm run test`(1回実行) / `npm run test:watch`(監視モード)

## 9. E2Eテスト方針(Playwright)

- 複数画面をまたぐ操作フロー(取引先の登録→一覧反映、エクスポート→復元)は、ユニットテストでは検証できないため、Playwrightの Electron 対応(`_electron`)でE2E基盤を整備する(ユーザー承認済み)。
- 対象環境はローカルのみ。本番環境・本番データには一切接続しない。テスト実行時は環境変数`JIMUHUB_DATA_DIR`でテスト専用の一時ディレクトリに保存先を切り替え、本番のデータベースファイルには触れない(`e2e/fixtures/electron-app.ts`参照)。
- OS標準の保存先選択・ファイル選択ダイアログはPlaywrightから直接操作できないため、環境変数`JIMUHUB_E2E_EXPORT_PATH`・`JIMUHUB_E2E_IMPORT_PATH`が設定されている場合に限り、Mainプロセス側でダイアログ表示を省略しそのパスを直接使用する(本番実行時はこれらの環境変数は設定されないため、通常どおりダイアログが表示される。`src/main/ipc/data.ipc-handler.ts`参照)。
- 実行コマンド:
  - `npm run test:e2e`(通常実行: ウィンドウを表示しない・高速)
  - `npm run test:e2e:headed`(見るだけ実行: ウィンドウを表示し、操作をゆっくり再生する)
  - いずれも実行前に`electron-vite build`を自動実行する(`pretest:e2e` / `pretest:e2e:headed`)。
- テストデータの後始末: DBファイルを直接操作せず、アプリ自身のUI操作・IPC API経由でのみテストデータを作成する。各テストは専用の一時データディレクトリを使い捨てで利用し、終了時に`fs.rmSync`で削除する(`closeApp`ヘルパー)。開発時の動作確認用サンプルデータ投入にも、直接SQLを書かず`src/main/dev/seed.ts`(`npm run seed` / `seed:reset` / `seed:clear`)を用いる。
- 証跡: スクリーンショット・トレースは失敗時のみ保存する(`playwright.config.ts`の`screenshot: 'only-on-failure'`・`trace: 'retain-on-failure'`)。

## 10. IPC設計方針

- チャンネル名は詳細設計書7章の一覧(`clients:list`等)をそのまま`src/shared/ipc/channels.ts`に定数化し、Main・Preload・Rendererで共有する。
- PreloadはcontextBridge経由で`window.jimuhubApi`のみを公開し、Rendererからのファイルシステム・Node.js直接アクセスは行わない(`contextIsolation: true`・`nodeIntegration: false`)。
- IPCハンドラ(`*IpcHandler`クラス)はApplication Service層を呼び出すだけの薄い層とし、業務ロジック・バリデーションはService層に置く。
- OS標準ダイアログ(保存先選択・ファイル選択・確認ダイアログ)の表示はMainプロセスでのみ行う。

## 11. エラーハンドリング方針

- 詳細設計書8章のエラーメッセージ文言は`src/shared/messages/messages.ts`に定数として一元管理し、Main・Renderer双方で同じ文言を使い回す。
- Application Service層は、業務エラー(例: 取引先が見つからない)を`Error`のサブクラス(例: `ClientNotFoundError`)としてthrowし、IPCハンドラでは個別にtry/catchせずElectronの`ipcMain.handle`の例外伝播に任せる(Rendererの`ipcRenderer.invoke`が例外を伴って reject されるため、呼び出し元でcatchしてメッセージ表示する)。
- ファイル入出力を伴う処理(エクスポート・復元)は、例外を投げず`{ success: boolean; error?: string }`形式の戻り値で結果を表現し、Renderer側で分岐して表示する。

## 12. コミット・作業単位

- 実装は機能のまとまり(例:「基盤+取引先管理」「データ管理(エクスポート/復元)」)ごとに完結させ、reviewerのレビューを経てから次のまとまりに着手する(ユーザー承認済みの運用)。
- コミットは、1つの機能のまとまりが仕上がった単位で作成する(コミットの実作成はユーザーが`/commit-push`で行う)。
