## 3. セットアップ手順

以下はすべて `app/` フォルダ内で実行するコマンドです。実際に実行して動作を確認済みです。

```bash
cd app
npm install          # 依存関係のインストール
```

### 起動(開発モード)

```bash
npm run dev           # electron-vite dev(ホットリロード付きで起動)
```

### ビルド(型チェック+本番ビルド)

```bash
npm run build          # tscによる型チェック → electron-vite build(out/ 配下に出力)
npm run start           # ビルド済みアプリのプレビュー起動(electron-vite preview)
```

### 配布用パッケージ(universal .dmg)の作成

```bash
npm run dist:mac        # electron-vite build → electron-builder --mac --universal
                         # release/事務HUB-<version>-universal.dmg が生成される
```

- Apple Developer Programには登録しておらず、未署名(unsigned)でビルドします(基本設計書7章・8.1章★A)。初回起動時の許可手順は、納品フェーズの操作マニュアルに記載します。
- 実際に `npm run dist:mac` を実行し、x86_64・arm64両対応のuniversal `.dmg` が生成されることを確認済みです。
- SEC-07対応として、他OS用ネイティブバイナリ・SQLiteのCソース・未使用のDB方言・ソースマップ等を配布物から除外しています(`electron-builder.yml`の`files`)。`app.asar`は25MB→5.0MB、`app.asar.unpacked`は30MB→5.1MBに縮小しました。
- 除外後の配布版(`--dir`ビルド)を実機で起動し、DB読み書き(better-sqlite3)・見積書/請求書のPDF生成が動作することを確認済みです。
- アプリアイコンはデザインガイド7.0節で確定した案C(`docs/04_design/mockups/icon-c_hub-cluster.png`)から生成した `resources/icon.icns` を `mac.icon` に設定しています。再生成する場合は、1024px PNGから `sips` で各サイズ(16〜512px・@2x)のiconsetを作り `iconutil -c icns` で変換します。
- 配布版の動作を確認する際は、実データ(`~/Library/Application Support/事務HUB`)を使わないよう、`--user-data-dir=<一時フォルダ>` を指定して起動してください(配布版は`JIMUHUB_DATA_DIR`を無視するため)。

### サンプルデータの投入(開発時の動作確認用、Q4回答: 通常は空の状態で起動)

```bash
npm run seed            # サンプル取引先5件を追加投入する(五十音順の確認用に先頭文字を分散済み)
npm run seed:reset       # 既存の取引先データを削除してからサンプルデータを追加する
npm run seed:clear       # 取引先データを削除するのみ
```

### テストの実行

```bash
npm run typecheck        # tsc --noEmit(Main/Preload/Shared, Renderer/Sharedの2系統)
npm run lint              # ESLint
npm run format:check       # Prettierチェック
npm run test               # Vitest(単体・画面操作テスト)を1回実行
npm run test:coverage       # カバレッジ付きで実行
npm run test:watch          # Vitestを監視モードで実行
```

### E2Eテストの実行(Playwright, Electronの実機起動)

```bash
npm run test:e2e          # 通常実行(ウィンドウを表示しない・高速)。ビルドを自動実行してから起動する
npm run test:e2e:headed    # 見るだけ実行(ウィンドウを表示し、操作をゆっくり再生する)
```

- 対象はローカルのみ。テスト専用の一時ディレクトリ(`JIMUHUB_DATA_DIR`)にデータ保存先を切り替えるため、本番のデータベースファイルには一切影響しません。
- OS標準のファイル保存・選択ダイアログはPlaywrightから直接操作できないため、E2Eテスト時のみ環境変数(`JIMUHUB_E2E_EXPORT_PATH`・`JIMUHUB_E2E_IMPORT_PATH`)でダイアログ表示を省略します(配布版(パッケージ済みの`.app`)ではこれらの環境変数・`JIMUHUB_DATA_DIR`を設定して起動しても無視され、通常どおりダイアログが表示されます)。

### テストフェーズの結合シナリオ(Playwright, tester作成)

上記の`e2e/tests`(developer作成、機能単体のE2E)とは別に、`e2e/scenarios`配下にテストフェーズ(tester)が追加した、詳細設計書ベースの機能横断シナリオ(結合テスト観点)があります。既存の`e2e/fixtures`を再利用し、専用の設定ファイル(`e2e/scenarios/playwright.config.ts`)で実行します。詳細は`docs/07_test/`配下のテスト成果物を参照してください。

```bash
npm run test:e2e:scenarios          # 通常実行(ウィンドウを表示しない・高速)
npm run test:e2e:scenarios:headed    # 見るだけ実行(ウィンドウを表示し、操作をゆっくり再生する)
```

## 6. 詳細設計書との差異

### 6.1 イテレーション0からの差異(継続)

| No | 内容 | 理由 |
|---|---|---|
| 1 | IPCチャンネル`app:startup-status`を追加した | 起動処理結果をRendererへ伝えるため。既存チャンネルの仕様に影響なし。 |
| 2 | E2Eテスト専用の環境変数(`JIMUHUB_E2E_EXPORT_PATH`・`JIMUHUB_E2E_IMPORT_PATH`)でOS標準ダイアログを省略する分岐を追加した | Playwrightからネイティブダイアログを操作できないため。配布版では無視する(SEC-01)。 |
| 3 | アプリのフォルダ構成を単一フォルダ`app/`にまとめた | Main・Preload・Rendererを1つの配布物にまとめるため。 |
| 4 | `JIMUHUB_WINDOW_SHOW`によるheaded/headless切り替えを追加した | E2Eの高速実行と見るだけ実行の切り替え。本番では常にウィンドウ表示。 |

### 6.2 イテレーション1(見積書・請求書作成)での差異

| No | 内容 | 理由・影響 |
|---|---|---|
| 5 | フリガナは全角カタカナのみ許可(ひらがな入力は自動でカタカナへ変換して保存)とした | ご本人のご判断。五十音順ソートの安定のため。設計書の入力制約に追加した制約。 |
| 6 | 自社情報・振込先の保存後は、一覧等へ遷移せず同じ画面に完了メッセージを表示する | 設定画面は繰り返し確認・修正する用途のため。画面遷移の記載があった場合の差異。 |
| 7 | PDFのHTML/CSSテンプレートはRendererのReactではなく、Main側(`src/main/services/pdf/`)の文字列テンプレートとした | `printToPDF`を行う非表示ウィンドウへ画面コードを持ち込まず、PDFの見た目を単独で検証・変更しやすくするため。 |
| 8 | 書類番号・ページ番号の繰り返し表示は、`printToPDF`の`footerTemplate`(ヒラギノ角ゴ指定)で実現した | 複数ページ時に全ページへ書類番号とページ数を出すため。本文内の固定要素では実現できない。 |
| 9 | PDFでは、明細に該当税率の行が1件もない場合、その税率の集計行(対象額・消費税額)を表示しない | ご本人のご指摘による改善。 |
| 10 | 請求書の源泉徴収税額は、行ごとではなく「源泉徴収対象の明細の合計額」に対して段階計算(100万円以下10.21%、超過分20.42%、円未満切り捨て)を1回だけ適用する。行単位の源泉徴収額は表示せず、`invoice_line_items.withholding_amount`列は常に0(未使用)とした | ご本人のご判断(例: 80万円+80万円=224,620円)。変換・エクスポート/復元に影響はない(列は0で保持される)。 |
| 11 | 確定処理は「下書き保存・採番・確定」を1トランザクションで行い、その後に非同期でPDFを生成する。PDF生成失敗時は`revertToDraft`(採番の巻き戻しではなく下書きへ戻す補償処理)で対応し、SQLのロールバックではない | PDF生成(別プロセス・ファイルI/O)をトランザクション内に含められないため。失敗時は番号が欠番になる場合がある。 |
| 12 | 業務ルールの検証(確定済み請求書のみ入金ステータス変更可、下書き見積書は請求書へ変換不可 等)を画面制御に加えてServiceでもガードした | 画面以外の経路(IPC)でも不正な状態遷移を防ぐため。 |
| 13 | トップ画面の「未収の請求書件数」は「確定済みかつ未入金」の請求書の件数と定義した | 設計書に厳密な定義の記載がなかったため。下書きは含めない。 |
| 14 | 復元時、ZIP内に該当PDFが存在しない書類は、ハッシュ不一致と同様に`pdf_hash_mismatch=1`として個別警告の対象とした | 設計書は「不一致」のみ記載。改変・欠落のどちらも検知できるように扱った。 |
| 15 | 起動エラー画面からの復元は、DB接続なしで動作する専用経路(`StartupRecoveryService`)とし、破損DBは世代管理せず退避ファイルとして保存した | ご承認済み(破損DBの退避は世代管理なしで可)。 |
| 16 | 復元ファイルに読み込み上限を設けた(ファイル1GiB、ZIPのエントリ10万件、展開後の宣言サイズ合計2GiB。超過時は「ファイルを読み込めません」と同じ解析エラー) | セキュリティチェック SEC-09(解凍爆弾・巨大ファイルによるメモリ枯渇の防止)。通常の利用規模では上限に達しない。 |
| 17 | 書類のPDFとして扱うのは拡張子`.pdf`のファイルのみとした(復元時、ZIP内の`.pdf`以外のエントリは書き出さず、`pdfPath`が`.pdf`以外なら`NULL`。「PDFを開く」「Finderで表示」も`.pdf`のみ) | セキュリティチェック SEC-10(細工した復元ファイルで、PDF以外のファイルをOSの既定アプリで開かせないため)。 |
